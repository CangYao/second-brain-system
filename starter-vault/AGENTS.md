# 第二大脑 · AI 协作规则

本文件适用于知识库根目录及所有子目录。AI 在本知识库执行任务时应遵循以下规则，并以用户的明确要求为准。

## 1. 目标与数据基础

“第二大脑”是一个长期个人知识系统，用于记录、整理和关联阅读、视频、知识、思想、个人经历、兴趣、观点变化和项目，并为未来知识图谱、SQLite 或其他结构化索引、Web App、Android App 及可能的 iOS App 提供结构化数据基础。

- Markdown 是主要数据格式，Obsidian 是主要浏览和编辑工具。
- Markdown 文件是长期保存的知识来源；未来索引和应用应能从文件及 Properties 解析数据。
- 保持文件结构、字段名称和字段类型长期稳定、可解析，避免无必要的格式变化。
- 内部关联优先使用 Obsidian Wikilink：`[[笔记名称]]`。存在同名笔记时使用明确路径，例如 `[[01_Knowledge/笔记名称]]`。
- 保留原始来源、URL，以及有助于追溯的作者、发布时间、阅读或观看日期；不得编造来源。

## 2. 现有目录与职责

| 目录 | 职责 |
| --- | --- |
| `00_Inbox` | 尚未整理的新资料、临时记录和待处理输入 |
| `01_Knowledge` | 核心知识、概念、人物及可复用的知识节点 |
| `02_Topics` | 主题组织、专题汇总和相关知识索引 |
| `03_Books` | 书籍记录、阅读笔记和书籍索引 |
| `04_Media` | 视频、文章及其他媒体资料记录 |
| `05_Personal` | 个人经历、思想、偏好及个人相关记录 |
| `06_Daily` | 每日重要事件、输入、想法、决定和观点 |
| `07_Timeline` | 重要个人事件、阶段和观点变化的时间线 |
| `08_Projects` | 项目目标、过程、决定、进展和成果 |
| `09_System` | 知识库规则、模板、系统说明和维护资料 |

遵循现有目录和相关索引的约定。目录职责不代表每次任务都需要创建文件或子目录，不得擅自进行大规模目录重构。

## 3. Inbox 与增量整理

所有尚未整理的新资料优先进入 `00_Inbox`，除非用户明确指定位置或资料已完成整理。

整理 Inbox 时依次执行：

1. 判断资料类型及适合的归属目录。
2. 提取核心信息，区分原文内容、个人表达与 AI 整理或推测。
3. 先读取相关索引，并在相关范围搜索已有知识和来源记录。
4. 优先补充、关联或更新已有笔记，避免重复创建语义相同的节点。
5. 必要时创建新的知识节点，并保持合适颗粒度。
6. 使用 `[[双向链接]]` 建立有意义的关联；需要时在相关笔记补充链接，不为链接数量制造关联。
7. 更新必要且已经存在的索引；确有需要时再创建索引。
8. 保留原始来源或 URL，保证摘要和知识节点可追溯。

整理不等于删除原始资料。移动、归档或清理应符合当前任务授权，未经明确要求不得批量删除文件。

## 4. 知识类型与颗粒度

`type` 至少支持以下稳定值：

| type | 含义 |
| --- | --- |
| `book` | 书籍与阅读记录 |
| `video` | 视频与观看记录 |
| `article` | 文章及文章笔记 |
| `concept` | 概念与知识卡片 |
| `person` | 人物记录 |
| `thought` | 思想、观点与反思 |
| `event` | 事件记录 |
| `project` | 项目记录 |
| `daily` | 每日记录 |
| `preference` | 已确认的个人偏好记录 |

知识卡片以“中等颗粒度为主，重要内容逐步原子化”为原则：

- 一篇笔记应围绕一个清晰主题，可以包含相互紧密关联的多个要点。
- 一本书可以产生若干核心概念笔记，并关联回书籍及来源。
- 重要概念后续可根据复用、关联和理解需要继续拆分。
- 不机械地将每句话拆成独立笔记，也不无必要地创建语义重复节点。

## 5. 书籍：Fiction 与 Nonfiction

书籍使用 `book_category` 区分 `Fiction` 和 `Nonfiction`，沿用已有目录约定，不因分类擅自建立或重构子目录。

- **Fiction**：小说、玄幻、仙侠、科幻等。重点记录人物、世界观、设定、情节、主题和个人评价。
- **Nonfiction**：思想、历史、科学、社会、经济等。重点记录核心问题、核心思想、论证、概念、个人理解和现实联系。
- 区分作者观点、作品内容、用户评价和 AI 分析，避免混写。

## 6. 个人内容与 AI 推测

个人相关内容必须明确区分：

- `fact`：有明确依据的事实，保留依据或来源。
- `preference`：用户已经确认的个人偏好，不从单次行为自动推定。
- `inference`：AI 根据资料作出的推测，必须显式标注。

知识类型 `type` 与个人内容性质 `personal_status` 是不同维度。例如，一篇 `thought` 笔记可以包含用户表达及 AI 推测，不能仅凭 `type` 判断真实性。

AI inference 不得自动视为事实，也不得写成用户的确定观点。每条推测必须记录：

- `confidence`：使用 0–1 的数值，表示推测置信度，不代表已确认。
- `evidence`：支持推测的资料、引用或笔记链接，并说明必要的推理依据。
- `updated`：最后修正日期，使用 `YYYY-MM-DD`。

整篇笔记性质一致时可使用 YAML Properties；混合内容应按段落或条目分别标注，推测各自携带上述字段。不得用一个笼统标记将混合内容全部视为事实。

根据用户反馈修正推测，记录修正日期及原因。只有获得明确依据或用户确认后，才可调整为 `fact` 或 `preference`，并保留必要的修正记录。

## 7. 观点演变与个人历史

不得直接覆盖旧观点，或无依据改写个人历史。当观点发生变化时，以带日期的条目记录：

- 当时观点。
- 后来的变化。
- 变化原因。
- 当前理解。

保留完整思想演变轨迹。可以更新“当前理解”摘要，但必须保留之前的表达及变化记录。未知的日期或原因应标为未知，不得补造。

## 8. Daily 与 Timeline

- `06_Daily` 记录每天的重要事件、阅读、视频、想法、决定和个人观点，并关联相关来源、知识或项目笔记。
- AI 可以根据当天内容提出少量有价值的问题，用于澄清、反思或推进决定；不要为了提问而提问。
- `07_Timeline` 记录重要个人事件、学习阶段、项目、旅行、阅读阶段和观点变化，关联详细记录。
- 区分事件发生日期与笔记创建日期；无法确定的日期不得伪装成精确日期。

## 9. YAML Properties 与长期解析

重要笔记应尽量具有稳定、结构化的 YAML Properties。优先沿用现有字段约定；新增字段应语义清晰、类型一致，避免多个字段表达同一含义。

建议按需要采用以下字段，不要求为无关内容填空字段：

| 字段 | 约定 |
| --- | --- |
| `id` | 每个知识对象的稳定唯一字符串标识；创建后不得因为标题、目录或文件名变化而改变 |
| `type` | 本文件定义的知识类型字符串 |
| `title` | 笔记标题字符串 |
| `created` | 创建日期，`YYYY-MM-DD` |
| `updated` | 实质内容最后更新日期；推测适用时为最后修正日期，`YYYY-MM-DD` |
| `tags` | 字符串列表 |
| `sources` | 原始 URL、来源描述或已加引号的 Wikilink 字符串列表 |
| `relations` | 已加引号的 Wikilink 字符串列表；为未来知识图谱的 typed relations 保留扩展空间 |
| `book_category` | 书籍适用：`Fiction` 或 `Nonfiction` |
| `personal_status` | 性质一致的个人内容适用：`fact`、`preference` 或 `inference` |
| `confidence` | 推测适用：0–1 数值 |
| `evidence` | 推测适用：依据字符串列表 |
| `date` | Daily 或事件适用：对应日期，`YYYY-MM-DD` |

建议的 `id` 格式：

- `book_<slug>`
- `concept_<slug>`
- `person_<slug>`
- `project_<slug>`
- `thought_YYYYMMDD_<序号>`
- `event_YYYYMMDD_<序号>`
- `daily_YYYYMMDD`

- YAML 必须语法有效；Wikilink 字段值应加引号，例如 `"[[笔记名称]]"`。
- 所有来源字段统一使用 `sources`，并始终采用列表格式，即使只有一个来源；`evidence` 用于记录推测依据，不另设来源字段。
- 列表字段保持列表类型，即使只有一个元素；未知信息可省略或明确标注，不编造值。
- 稳定 ID 与现有有效 Properties 不得随意重新生成或改名。
- 不为补齐 Properties 擅自批量改写整个知识库。
- 为 SQLite、知识图谱及各端应用保留可解析的标识、类型、日期、来源与关联信息。

## 10. 修改边界与执行方式

禁止以下行为：

- 未经明确要求批量删除文件。
- 无依据覆盖个人历史观点。
- 把 AI 推测写成用户的确定观点。
- 无必要创建语义重复的知识节点。
- 擅自进行大规模目录重构。

大规模修改前，必须先分析影响范围、给出修改计划、明确涉及哪些目录和文件，并获得用户确认后再执行。大规模修改包括跨多个目录的批量迁移、批量字段或链接变更、系统性重命名和目录重构等；不得把此要求扩大为每次日常增量编辑都需要确认。

当用户以自然语言提出知识库相关任务时，优先读取并遵循 `09_System/Workflows/ROUTER.md`，由 `ROUTER.md` 判断任务类型，并按对应 Workflow 执行。

日常任务的最小读取层级、对象匹配与完成判定统一引用 `09_System/Workflows/CORE-CONTRACT.md`；按需读取，不默认扫描全库。

Personal Model 的按需读取、准入、证据、冲突和更新协议统一引用 `09_System/Workflows/Personal-Model.md`，并遵守 CORE-CONTRACT 最小读取原则；普通事实任务不读模型，普通推荐／规划不自动写回，只有明确更新授权才执行 personal_model_update。

## 自动执行边界

- 在当前任务授权范围内，可直接创建／增量更新 Markdown、YAML、整理指定 Inbox、局部搜索、调用已有 canonical 工具、在 Temp 创建任务中间产物并作非破坏性验证；这不是任意改写内容或无限网络请求的授权。
- 删除正式笔记、大规模移动／重命名、安装软件、修改系统环境或 canonical path、删除 Backup、大规模 Obsidian 配置变更、新建基础设施层，须先明确影响与方案并取得确认。用户已明确授权且范围一致时无需重复确认。
- QuickAdd 是 Obsidian 内人工快速入口，只用已有 Template／创建脚本；Codex 是自然语言整理入口，遵循 Workflow／Template／canonical dependencies。共享数据结构，不在两端各维护完整业务实现。

## 11. Git checkpoint 与回退

- 普通小改动（单个笔记、小范围文字修正、Daily / Book / Video / Thought 增量更新）开始前执行 `git status`；无需每次创建 checkpoint，完成后报告实际变化的文件。
- 结构性或高风险修改前必须执行 `git status`：批量修改多个文件；修改 AGENTS.md、ROUTER.md、Workflows、Templates、Personal Model 结构、目录结构、自动化脚本、SQLite / 索引生成逻辑；批量重命名、移动、删除；插件配置大范围变更。普通日常增量任务关联更新少量笔记，仍按小改动处理。
- 工作区 clean 时，允许先创建 checkpoint，信息格式为 `checkpoint: before <简短任务名>`。clean 表示没有待提交内容；确需新增命名恢复点时可使用 `git commit --allow-empty`，不改动文件。checkpoint 不替代大规模修改所需的用户确认。
- 结构性或高风险任务开始时若工作区不 clean，不擅自暂存或提交已有改动；报告当前未提交文件、修改类型（新增、修改、删除及是否已暂存）、与本次任务的关联；等待用户确认后再继续相关写入。
- 结构性任务完成后执行 `git status`、`git diff --stat`，必要时检查 `git diff`；若已有暂存内容，同时检查对应的 `git diff --cached --stat` / `git diff --cached`。报告新增、修改、删除文件；除非任务明确要求，不自动创建最终 commit。
- 默认禁止 `git reset --hard`、`git clean -fd`、`git push --force`、`git rebase`、`git filter-branch`、`git filter-repo`、删除 `.git`、修改历史 commit，以及未经确认删除未提交工作。
- 撤销未提交改动时先明确授权及具体文件，优先使用 `git restore <具体文件>`，仅恢复本次获准撤销的内容；不默认使用 `git restore .` 或 `git reset --hard`。回退已提交版本时，先报告目标 commit、回退方式及影响范围，等待用户确认后执行。
- 调用本地工具前优先查询 `09_System/Config/tool-registry.local.json` 并核实路径；已有适用工具时复用，不得无理由复制已有工具。
- Git 层保持最小化：不引入 hooks 或复杂自动化脚本；未经明确要求，不修改全局配置、不配置远程、不 push、不创建额外分支。
- 涉及系统结构、新工具、新 Workflow、新 Script、新 Skill、新模型、新自动化或 canonical path 修改时，先读取 `09_System/System-Map.md`；涉及外部工具时同时读取 `09_System/Config/tool-registry.local.json`，优先复用现有组件，不为单次任务复制已有工具、模型或完整实现。

## Public bootstrap

机器配置由 setup 生成于 `09_System/Config/local.json`；工具路径以 `tool-registry.local.json` 为准。视频中间产物由显式外部 temp_root/cache_root 管理，不放入 Vault。没有本地 Git 仓库或身份尚未配置时，知识任务仍可执行，Git 收尾报告 NOT_CONFIGURED；不静默初始化、设置身份或配置远端。
